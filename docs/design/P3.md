# P3 — MD-VDP SPRITE OFFLOAD (design, 2026-08-28)

Charter (docs/design/REBUILD.md 2026-08-26): the frame doesn't fit because both
SH-2s software-draw every actor while the MD VDP's sprite engine — 80
hardware sprites, 20/line, rendered by silicon — sits idle. Move the
mob classes there; SH-2 keeps zoomed actors + player + cat1 + text.

Everything below is recon-verified with citations (three read-only
passes, 2026-08-28). Design decisions are marked DECIDE; open
questions carry their measurement.

## The economics (discover/play.csv, 52,001 record-draws)

Clustered by S16 colour set (= actor class proxy), native 1:1 records:

    set 0x00 (w4 F380, mob walker, 6 keys)   25.5%   6.9 KB MD art
    set 0x10 (F390, 14 keys, small)          10.5%   2.6 KB
    set 0x0B (F38B, 7 keys)                   9.1%   1.6 KB
    set 0x0A (F38A, 10 keys)                  9.1%   3.8 KB
    set 0x07 (F487, ONE 74x37 key)            6.3%   1.6 KB
    ---- cheap five                          60.5%  16.5 KB
    set 0x0F/0x02 (player-class, 79 keys)    21.3%  65   KB  <- stays SH-2

The full native set is 196 KB MD-format vs ~19 KB free VRAM: full
offload is impossible, and unnecessary — the mob classes are where
the per-frame volume is. The player is ONE record per frame (cheap
for compose, ruinous for VRAM): it stays SH-2 forever.

## Hardware facts the design rests on (all cited in recon reports)

1. **MD CRAM line 0 (entries 1-15) is FREE.** Boot writes a ramp that
   never displays (md_main.c:120-139); nothing touches it after.
   Lines 1-3 are the BG pen allocator's (m_main.c:242,266).
2. **~19KB VRAM free**: 0x8000-0xAFFF (12K), 0xD000-0xDFFF (4K),
   0xF000-0xFBFF (3K). Tile-upload guard already admits va<0xB000
   (md_main.c:484,585).
3. **SAT reg5 says 0xFE00 but NOTHING ever writes the table**
   (invisibility rides emulator-zeroed VRAM — real-HW garbage risk),
   and ares masks the H40 SAT base to 1KB alignment, which would
   alias 0xFE00 onto 0xFC00 = the HSCROLL TABLE. DECIDE: move SAT to
   0xF000 (1KB-aligned, in free VRAM), zero it at boot. The spike
   verifies.
4. **The SH2->68K channel is FB-window packets consumed by VDP DMA at
   FM=0 in vblank** (md_main.c:1103-1114, DMA idiom :460-470). The
   sprite table is ONE more DMA next to the existing two consumes.
   The 68K classifies NOTHING.
5. **Record format**: native iff (w5 & 0x3FF)==0 (m_main.c:2604); pp =
   (w4>>6)&3; set = w4&0x3F; **w2 bits 9-13 unread by every consumer**
   — free claim-bit storage in SPR_SNAP (our copy; marking happens
   post-copy at the harvest fill, m_main.c:6597-6610, the one
   frame-coherent site).
6. **S16 priority (jts16_prio.v:84-95 == our level model)**: pp=2
   beats BG both cats + FG cat0, loses to FG cat1 + text. pp=3 also
   beats FG cat1/text cat0. pp<=1 loses to BG cat1/FG cat0.
7. **32X mix**: an MD sprite behaves exactly like the MD planes — FB
   pixels ALWAYS cover it; it sorts against MD planes by SAT priority
   bit (ares dac.cpp:21-22).
8. **MD sprite**: 8-byte SAT entry, 4 tiles max each dimension
   (32x32), tiles column-major (tileNumber = tileX*heightInTiles),
   4bpp 32B/tile, pen 0 transparent. H40: 80 total, 20/line, 320
   sprite-px/line. S16 pens are 1..14 (+0 transparent, 15=strip
   sentinel that never draws): **fits an MD 15-color line exactly.**
9. **Art transit**: SH-2 reads baked cart data freely (RV=0 model);
   VRAM writes go cart -> SH-2 -> FB staging packet -> 68K VDP-DMA.
   Never DMA from cart windows (unconfirmed, NOTES.md:403-407 RV
   hazard) — always through the FB window like everything else.

## Priority mapping (v1)

Claim ONLY pp==2 records ("pp=2 dominant", census pp histogram will
quantify). SAT priority bit = 1 on every claimed sprite:

    vs MD planes (BG both cats, FG cat0):  sprite wins  = S16 exact
    vs FB (FG cat1, text, SH-2 sprites):   FB wins      = S16 exact*

(*) Two inherited/accepted inaccuracies, both counted not guessed:
pp=3-over-FG-cat1 cannot be expressed MD-side (pp=3 stays SH-2 in
v1); sprite-vs-sprite: an SH-2 sprite always covers an MD sprite even
when the S16 list order says otherwise (mob-over-player piles). A
DIAG counts claimed-record bbox overlaps with later unclaimed records;
if the count is material in play, the overlapped record un-claims for
that frame (cheap, per-frame).

pp<=1 sprites (behind FG cat0) are expressible later by carrying the
S16 cat bit into MD plane priority bits, but that entangles plane-vs-
plane order — out of v1's scope, measured need first.

## The pipeline (v1 = flag MDSPR, rides the DIRECTFB build)

**Bake (offline)**: extend the bake pipeline (same decoder that
already passes byte-identical replay): for the chosen classes emit
column-major 4bpp MD tiles per key, split into per-HW-sprite
subsprite runs {dx,dy,wtiles,htiles,tile_off}, packed blob + index in
cart ROM. v1 classes: set 0x00 (6.9K) + 0x10 (2.6K) + 0x0B (1.6K) =
11.1 KB = 347 tiles, fits the contiguous 12K block at 0x8000.

**Art residency (v1: static preload)**: at boot/scene start the SH-2
streams the whole class set through the existing tile transport into
0x8000+ (guard already allows it). Until resident, records simply
aren't claimed — SH-2 composes them, display is correct from frame 1.

**Palette**: MD line 0 tracks the LIVE S16 palette of the claimed
sets, quantized 3-bit/channel exactly like the BG pens (mdp_quant),
shipped in the existing CRAM DMA block widened 48->64 words. Fades on
mobs keep working. v1 claims sets ONLY while their palette equals the
one line-0 track... v1 tracks ONE set's palette (0x00, the 25.5%
class); sets 0x10/0x0B claim only if their live palette words are
IDENTICAL to set 0x00's (measured: sometimes true in S16 games) —
else they stay SH-2. Line count grows in v2 by shrinking MDP_LINES
3->2 if the pen-pressure counter says the BG allocator can spare it.

**Claim + SAT build (SH-2, master, once per frame at the harvest fill
site)**: walk SPR_SNAP; for each record: native && pp==2 && set
resident && art resident && caps (<=64 sprites, <=18/line estimated,
overlap rule) -> set w2 bit13, emit SAT entries (x=xpos-184+128,
y=top+128, size/tiles from the index, pal line 0, prio 1, link
chain). Write the SAT image into a fixed FB staging packet. Claimed
records' pixels never touch compose, the erase pass, or the FB.

**68K (vint, FM=0, next to the existing consumes)**: one VDP DMA,
SAT packet -> VRAM 0xF000. Boot: reg5 -> 0xF000, zero the table
(also closes the real-hardware garbage risk).

**Compose**: bit13 test lands beside the existing bit14 hide test
(m_main.c:2457) — one masked compare, zero cost for SH-2 sprites.

## Ceilings (census-backed)

Mean 2.78 HW sprites per native record; F380 mobs are 2x2 (36-40 x
48-64) = 4 entries. 5-6 mobs + objects ~ 24-30 SAT entries, vs caps
80/64. Per-line: 6 actors abreast = ~12 sprites/line, 200 px/line —
inside 20/320. The claim pass keeps running totals and stops
claiming at the caps; overflow actors just stay SH-2 that frame.
tools/sprite_census.lua re-run (2026-08-28) regenerates the per-line
histogram from the arcade oracle; the in-tree SLC probe (m_main.c:
438-481, LOOP18) measures the same on OUR runtime when needed.

## What this buys (and the honest bound)

v1 (three classes, one palette line): ~45% of native record-draws
eligible by art, gated by the palette-identity rule to >=25.5%
(set 0x00 alone). Every claimed record leaves compose, the FB, the
erase pass, and the DREQ-adjacent bus traffic. The chain's sprite
phase and FB coverage shrink proportionally; compose-skip (43.0% on
DIRECTFB stage 2) is THE number M3 gates on. v2 levers, in order:
second palette line (MDP_LINES 3->2), set 0x0A/0x07 classes (+15.4%,
+5.4KB into 0xD000 after guard widening), pp=3 class, per-scene
residency swaps.

## M0-M2 EXECUTION LOG (2026-08-28, one session)

M0 VERIFIED: SAT moved 0xFE00->0xF000 (H40 alignment masking would
have aliased the old base onto the HSCROLL table; also never zeroed —
real-HW garbage hole, closed), two test sprites rendered over planes
and under Zeus's FB pixels. One build answered all three mixing
questions.

M1 VERIFIED: bake_mdspr.py (reuses the replay-gated decoder) -> MD
tiles, blob pinned at cart 0x2F0000, 68K boot-uploads via temp bank-2
window; byte-identical in VRAM on ares. Offline render with the exact
ares patternFetch algorithm: 0 mismatched pixels.

M2 LANDED, three bugs found and killed on the way:
  - DIAG minefield hits #10 AND #11: [53]/[54] taken (md_tag/pages),
    then [10]/[11] taken (diag_add band phases). Counters live in the
    MDSPR scratch tail (0x3A520) now. NOTHING in DIAG 0-63 is free.
  - ANCHOR FLAPPING: "first claimable record's set" changes with list
    order per frame; SAT/CRAM generations desync and mobs draw in the
    other class's palette (the white zombie). Anchor is STATIC now.
  - v1 CLASS SELECTION WAS WRONG: whole-corpus draw counts picked
    scene-clustered scenery — claims were ZERO through the entire
    gameplay stretch (900-1600). v2 bakes set 0x09 (the zombies, 8
    keys 6.9KB, 91% of the class in 4 walk keys) and anchors line 0
    to it; claims now flow exactly where the load is (~1.1/frame).

LINE-STEAL IS DEAD BY MEASUREMENT: BG allocator lines are 1/1/4 pens
free across attract/gameplay/graveyard — a 16-pen steal would evict
live BG colours. One MD palette line is all this design gets until
the pen allocator itself is renegotiated.

GATES (1900f battery + 920f paired sweep, all vs stage-2 baseline):
      bad1 65 (BEST EVER; stage-2 77, canonical 138)
      HUD dropouts 70 (BEST; 113 stage-2, 233 canonical)
      cadence 1.048 / rejects 2.15 / skips 0 / purple 0
      compose-skip 44.5% vs 43.0 — THE number, basically unmoved
      STRIP 151 vs 129 (v1-scenery arm measured 94) — scene-dominated,
      possibly worsened by fresh-MD-vs-held-FB contrast on movers
      68K handler 101.8 (+2 lines: the two DMAs + claim pass)

HONEST BOUND: ~4.7 records/frame exist (census); zombies are ~1.1.
The offload machinery is PROVEN end to end, but at this claim rate it
relieves ~20% of the sprite phase — not enough to make compose fit
the frame. The scaling lever is PLAYER-CLASS art (65KB, VRAM-
impossible statically): STREAMING residency — upload the current
animation frame (~2-4KB) through the existing 12-40 tile/vint
transport with bake-ordered prediction. That is the per-scene-bake
family and the real P3 continuation.

SHIPPING CALL: rom/s16.32x stays the stage-2 DIRECTFB build (best
STRIP line, Mike's #1 defect). MDSPR remains a flag build; its bad1
and HUD wins ride along whenever it next ships. Flags: MDSPR=1
(+MDSPRDOUBLE=1 bisect aid, never ship).
